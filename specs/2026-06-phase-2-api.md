# Spec: Phase 2 — API + persistence (minimal spine)

Status: implemented · Branch: `feat/phase-2-api` · Date: 2026-06-19

Stands up `apps/api` (Fastify) + a persistent kernel so a submission **survives a refresh** and
the **PDF is server-made and served from storage**, per `docs/ROADMAP.md` Phase 2. Minimal spine
only — kernel tables, not module tables.

## What changed & why

### 1. `apps/api` — Fastify service
- **What:** A new workspace `apps/api` consuming `@fbsi/shared`. `buildApp(config, database)` wires
  the kernel slices; `server.ts` runs migrations on boot and listens. `@fastify/cors` allows the web origin.
- **Why:** The frontend must talk only to our API (invariant 4); business logic + the canonical PDF
  live server-side.

### 2. Env-driven Drizzle DB (runs locally with zero infra)
- **What:** `db/client.ts` picks the driver from env — `DATABASE_URL` → Postgres via `postgres-js`;
  unset → embedded **pglite** (file-persisted for dev, `:memory:` for tests). One schema + one set of
  migrations (`drizzle/0000_*.sql`, generated by drizzle-kit) serve both, applied by `db/migrate.ts`.
- **Why:** Supabase becomes a deployment detail, not a code dependency; the DoD is verifiable here
  (no Docker/cloud), and tests run against a real Postgres engine.

### 3. Shared kernel schema (minimal)
- **What:** `db/schema/kernel.ts` — `organization`, `plan`, `cases` (answers **JSONB**) with nullable
  `owner_id` ownership columns. FKs point toward the kernel (`plan`/`cases` → `organization`,
  `cases` → `plan`). No module tables.
- **Why:** Tier-0 kernel only; questionnaire fields stay in JSONB (Tier-2, no migration to add fields).

### 4. Cases slice + server-made PDF + storage
- **What:** `kernel/cases/{store,service,routes,index}.ts`. `service.create()` re-runs the shared
  `validate()` (invariant 3) + a Zod envelope, persists org/plan/case atomically, renders the
  Onboarding Package via `renderToBuffer` (`pdf.ts`), and stores it via `PdfStorage`
  (`LocalPdfStorage` now; `SupabaseStorage` documented for prod).
- **Endpoints:** `POST /api/cases` → `{id, pdfUrl}`; `GET /api/cases/:id`; `GET /api/cases/:id/pdf`.

### 5. Frontend integration (posts, with fallback)
- **What:** `apps/web/src/api.ts` client; `App.tsx` POSTs on submit, stores the case id in the URL
  (`#case=<id>`) so a refresh reloads it from the API, and links to the server PDF. If the API is
  unreachable it falls back to local generation so the app still works standalone.

## Verify (DoD)
- `pnpm -r typecheck` · `pnpm lint` · `pnpm -r build` · `pnpm -r test` (5 API tests, pglite).
- Live: boot `pnpm --filter api start`, `POST /api/cases` → `GET /api/cases/:id` (answers round-trip)
  → `GET /api/cases/:id/pdf` returns `%PDF…` bytes from storage.
- Browser: submit → reload (`#case=<id>`) restores the done screen from the API.

## Deferred
- **Phase 3 (ask-once cross-session):** look up an existing organization/plan and pre-fill; collect
  only the delta. (Today `create()` always inserts a new org/plan.)
- **Phase 4 (auth + signatures):** Supabase Auth populates the `owner_id` columns; append-only
  signature audit log; RLS by `organization_id`.
- **Prod infra:** point `DATABASE_URL` at Supabase Postgres and implement `SupabaseStorage`
  (S3-compatible) — both already isolated behind the driver/storage seams.
